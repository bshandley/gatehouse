Dynamic Secret Providers

Gatehouse ships with five dynamic secret providers. Each provider has its own configuration schema and a different set of required privileges on the target system.

A config is created with POST /v1/dynamic (admin) or through the web UI. The body is { "path", "provider_type", "config" }, and every value inside config is a string: lists such as grants and principals are comma-separated.

PostgreSQL#

Creates a time-bounded role with the privileges you specify, then drops the role when the lease expires.

Required privileges on the connection user: CREATEROLE plus any privileges you want to grant the ephemeral users.

Example config:

{
  "path": "db/postgres-prod",
  "provider_type": "postgresql",
  "config": {
    "host": "db.internal",
    "port": "5432",
    "database": "appdb",
    "user": "gatehouse_admin",
    "password": "admin-password",
    "grants": "SELECT,INSERT,UPDATE",
    "schema": "public"
  }
}

Required: host, database, user, password. Optional: port, grants, schema, ssl, ssl_ca.

MySQL / MariaDB#

iNote

MariaDB and some MySQL versions reject parameterized placeholders in DDL. Gatehouse uses quoted string interpolation with proper escaping for user@host identifiers.

Required privileges on the connection user: CREATE USER, GRANT OPTION, plus any privileges you want to pass through.

Example config:

{
  "path": "db/mysql-prod",
  "provider_type": "mysql",
  "config": {
    "host": "db.internal",
    "port": "3306",
    "database": "appdb",
    "user": "gatehouse_admin",
    "password": "admin-password",
    "grants": "SELECT,INSERT",
    "allowed_host": "%"
  }
}

Required: host, database, user, password. Optional: port, grants, allowed_host, ssl, ssl_ca.

MongoDB#

Uses db.createUser() and db.dropUser() with the root role on the admin DB (or any role with userAdminAnyDatabase).

Example config:

{
  "path": "db/mongo-prod",
  "provider_type": "mongodb",
  "config": {
    "host": "mongo.internal",
    "port": "27017",
    "database": "appdb",
    "user": "gatehouse_admin",
    "password": "admin-password",
    "roles": "readWrite",
    "auth_source": "admin"
  }
}

Required: host, database, user, password. Optional: port, roles, auth_source, ssl.

Redis#

Uses Redis ACLs (ACL SETUSER, ACL DELUSER). Requires Redis 6.0+.

Example config:

{
  "path": "cache/redis-prod",
  "provider_type": "redis",
  "config": {
    "host": "cache.internal",
    "port": "6379",
    "password": "admin-password",
    "commands": "+@read +@write",
    "keys": "~app:*"
  }
}

Required: host, password. Optional: port, db, commands, keys, ssl, ssl_ca.

SSH certificates#

Signs ephemeral SSH certificates with a CA key stored in Gatehouse. Agents present the certificate to the target host, the host verifies the certificate against the CA public key, and the agent is allowed in for the certificate’s validity period.

Setup:

  1. Click Generate New CA Keypair in the dynamic secrets config modal. Gatehouse generates an ed25519 CA keypair and shows you both the private and public keys.
  2. Copy the CA public key.
  3. On each target host, add the CA public key to /etc/ssh/ca.pub and reference it in /etc/ssh/sshd_config with TrustedUserCAKeys /etc/ssh/ca.pub.
  4. Restart sshd.
  5. Back in Gatehouse, specify the principals (SSH usernames) the certificate should be valid for. Without principals, certs default to the agent’s AppRole identity, which won’t match any real SSH user.

Example config:

{
  "path": "ssh/prod-servers",
  "provider_type": "ssh-cert",
  "config": {
    "ca_private_key": "-----BEGIN OPENSSH PRIVATE KEY-----\n...\n-----END OPENSSH PRIVATE KEY-----",
    "principals": "deploy,readonly",
    "extensions": "permit-pty,permit-port-forwarding"
  }
}

Required: ca_private_key. Optional: principals, extensions, allowed_hosts. There is no validity setting in the config: a certificate is valid for the TTL requested at checkout.

allowed_hosts is advisory. It is a comma-separated list of hosts (for example 10.0.0.107,db.lab) that tells the agent where to connect. Gatehouse does not enforce it: SSH certificates are not scoped to hosts, so the signed certificate works on any host that trusts your CA, and signing never checks the list. The value is shown to agents in the metadata of their secret list entry and in credential.allowed_hosts on the checkout response (omitted when empty). Whether a host accepts the certificate is decided by that host’s TrustedUserCAKeys and the principals. To limit where an agent can log in, restrict it on the hosts (trusted CA, principals, AuthorizedPrincipalsFile), not here.

To see which provider types a server supports, call GET /v1/dynamic/providers (any authenticated caller). It returns { "providers": [...] }.
