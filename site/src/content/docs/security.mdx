Gatehouse is designed for the homelab threat model: a single operator, one or more AI agents with varying degrees of trust, and a small set of credentials worth protecting. This page documents what the system protects against and the assumptions it relies on.

## What Gatehouse protects

- **Credential leaks from agent context windows.** Proxy mode keeps the key server-side. The agent only sees the API response.
- **Secret sprawl.** All credentials live in one place with a single audit log.
- **Static credential exposure.** Dynamic secrets eliminate long-lived database and SSH credentials.
- **Privileged token misuse.** Per-agent AppRoles with scoped policies replace shared tokens.
- **Accidental logging of credentials.** The scrubber catches 15+ common credential formats in MCP and REST responses.
- **Encryption at rest.** Every secret is encrypted with a per-secret DEK, which is encrypted with a KEK derived from the master key via HKDF-SHA256.

## What Gatehouse does not protect against

- **Host compromise.** If an attacker gets root on the container host, they can read the master key from process memory, `/proc/$PID/environ`, or via `docker inspect` if the master key is set as an env var. Gatehouse reads the master key from `GATEHOUSE_MASTER_KEY` or, when that is unset, from `master.key` in the data volume (there is no Docker secrets option). A key file means anyone who can read the volume has the database and the key together, so limit who can reach the Docker socket and the host.
- **A malicious admin.** An admin user with the `admin` capability can read any secret and revoke any lease. The audit log records what they did, but it does not prevent them.
- **Side channels in upstream APIs.** If an agent proxies a request and the upstream API includes the credential in its response (a misconfiguration on the upstream's side), Gatehouse cannot un-leak it.

## Deployment recommendations

### Master key handling

Gatehouse writes a master key to disk in three cases, always as a 0600 file in the data volume:

- **First boot** with no `GATEHOUSE_MASTER_KEY` and no database: the generated key goes to `master.key`.
- **Key rotation on a key-file install**: the new key replaces `master.key`, the old one stays beside it as `master.key.pre-rotate-<timestamp>`, and a rotation that stops partway can leave `master.key.next`. An env-key install writes nothing.
- **A sealed import** with `GATEHOUSE_MASTER_KEY` unset: the bundle's key is written to `master.key`, and a different existing one is kept as `master.key.pre-import-<timestamp>`.

The leftover `pre-rotate` and `pre-import` files hold old keys, so delete them once you no longer need old exports or the rollback. Losing the key means losing access to every encrypted secret. Store the master key:

- **For homelabs:** in a password manager separate from the one that holds Gatehouse credentials, plus a printed backup in a safe place.
- **For higher-trust deployments:** set `GATEHOUSE_MASTER_KEY` and delete `master.key`, so the key is not in the same volume as the database. The key is then an env var, so it is visible in `docker inspect` output and `/proc/$PID/environ`. Inject it at container start from your secret store rather than keeping it in a compose file or `.env` on disk, and restrict access to the Docker socket.

<Callout type="warning" title="Do not check in your master key">
  The master key is a 32-byte secret. Never commit it to a git repo, never paste it into Slack, never send it in an email.
</Callout>

Backup, export and restore are covered in [Backup & Recovery](/docs/backup/).

### Root token handling

A root token bypasses every access control check. It exists only to create the first admin. Where it comes from, in order:

1. **`GATEHOUSE_ROOT_TOKEN` is set and not empty or whitespace.** It is the root token and always wins. Gatehouse never generates, writes, or deletes anything for it, and it never retires on its own. Remove it from your `docker-compose.yml` or `docker run` command, and restart, once you have an admin user.
2. **An admin exists** (an enabled admin user, or a non-suspended AppRole holding the `admin` policy). There is no root token. A leftover `bootstrap-root.token` is deleted at startup and never loaded.
3. **No admin, and `bootstrap-root.token` exists.** The saved token is reused, so restarting before you have created an admin does not change it.
4. **No admin, no file.** Gatehouse generates a token (16 random bytes, 32 hex characters), writes it to `${GATEHOUSE_DATA_DIR}/bootstrap-root.token` (mode 0600, default `/data`), and prints it once to the container log (stderr) under `GATEHOUSE BOOTSTRAP ROOT TOKEN`. If the data directory is not writable, the banner says `NOT SAVED` and the token is lost on restart.

The bootstrap token retires on the first restart after an admin exists, not the moment you create the admin. Until that restart it still works. Create your admin, confirm you can sign in as that user, then restart the container once.

`GET /v1/config` reports the active source as `root_token_source`: `env`, `bootstrap` (generated or reused from disk), or `null` when there is no root token.

Rule 1 is checked before rule 2, so while `GATEHOUSE_ROOT_TOKEN` is set a leftover `bootstrap-root.token` is left alone. If you later remove the env token while no admin exists, that file becomes the active root token again.

**Locked out?** Set `GATEHOUSE_ROOT_TOKEN` to a fresh random value (`openssl rand -hex 32`) and recreate the container (`docker compose up -d`; a plain restart does not pick up an environment change). Sign in with it, fix or create your admin, then remove the variable and recreate the container again.

<Callout type="warning" title="Upgrading from an older compose file">
  Before 0.23.0 the reference `docker-compose.yml` contained `GATEHOUSE_ROOT_TOKEN=${GATEHOUSE_ROOT_TOKEN:-gatehouse-root-changeme}`. That default lived in your compose file, not in the image. Pulling the new image does not touch your compose file, the env token wins, and the publicly known token `gatehouse-root-changeme` stays active. The old `.env.example` carried the same value, so a `.env` copied from it has it too. It stops working only once neither your compose file nor your `.env` supplies `gatehouse-root-changeme`. Remove it from both now, then recreate the container with `docker compose up -d` (a plain restart keeps the old environment). Check with `docker compose config | grep GATEHOUSE_ROOT_TOKEN`: it must not print `gatehouse-root-changeme`. That reads your files, not the running container, so also confirm the startup WARNING is gone from `docker logs gatehouse`: Gatehouse logs it on every start while the token is active.

  If there is no enabled admin user, no active (non-suspended) admin AppRole, and no env token, first boot of 0.23.0 generates a bootstrap root token and prints it to the container log. Create an admin and restart to retire it. If you set your own `GATEHOUSE_ROOT_TOKEN` (in `.env` or elsewhere), or your own `GATEHOUSE_MASTER_KEY`, it still wins: a non-empty value always does. Remove your own root token once you have an admin.
</Callout>

### Policy discipline

Give each agent its own AppRole with the minimum capabilities it needs. An agent that only reads from `api-keys/*` should not have `delete` or `admin`. The web UI makes it easy to inspect which policies each AppRole references and what paths each policy covers.

### Network exposure

Gatehouse listens on port 3100 by default. For homelab use, keep it on a private network. If you must expose it to the internet, put it behind a reverse proxy with TLS (Caddy, nginx, Traefik) and consider IP allowlisting on the proxy.

Slow readers: under Bun, a client that connects and then stops reading its response is bounded in bytes but not in time. The server's idle timeout does not fire while unsent response data is waiting, so the connection stays open. This applies to every route. Passthrough also turns Bun's per-request idle timeout off for its responses (so a quiet stream is governed by `max_timeout_ms` instead), which means that on `/p/` the byte cap (`max_body_bytes`) bounds what is buffered and a reverse-proxy send timeout is the only time bound. For an exposed deployment, put a reverse proxy with a send timeout in front (nginx `send_timeout`, for example) so such connections are closed.

### Trusting the client IP behind a proxy

The client IP drives every network-origin control: AppRole IP allowlists, the rotate-token IP allowlist, and the lease/proxy `auto_approve_from_ip` gate. Because `X-Forwarded-For` is just a request header, Gatehouse honors it only when the request's immediate TCP peer is a trusted reverse proxy. Otherwise the real socket address wins, so a client that sets its own `X-Forwarded-For` cannot impersonate a trusted network.

Loopback (`127.0.0.0/8`, `::1`) is always trusted, which covers a reverse proxy running on the same host. If your proxy is on a separate host or a Docker network whose gateway is not loopback, list its address in `GATEHOUSE_TRUSTED_PROXIES` (comma-separated CIDRs, additive to the loopback defaults). When a forwarded chain is present, Gatehouse walks it right-to-left and takes the first hop that is not itself a trusted proxy as the real client.

If you run behind such a proxy and rely on IP allowlists or auto-approve but leave `GATEHOUSE_TRUSTED_PROXIES` unset, these controls fail closed: the source IP becomes the proxy's address, allowlisted logins are denied, and auto-approve falls back to the human approval flow. Direct-connection deployments need no configuration.

### Proxy hardening

The proxy (`POST /v1/proxy` and the MCP `gatehouse_proxy` tool) lets agents call upstream HTTP APIs without ever holding the credential. Three layers of scoping apply, in order:

1. **Policy.** The agent's AppRole must have the `proxy` capability on the secret it wants to inject. No policy match, no proxy call.
2. **`allowed_domains` per secret.** Restricts which hosts the secret can be forwarded to. A secret with `allowed_domains = "api.openai.com"` cannot be used to call `evil.com` even if the agent's policy allows proxy on it. An entry is a domain (which covers its subdomains), `*.domain`, `host:port`, or a CIDR range, and the list is validated when the secret is written.
3. **`allowed_path_prefixes` per secret.** Restricts which URL paths a secret can hit, useful for scoping a broad credential (e.g. a fine-grained GitHub PAT) to a single repo's API surface. Match is path-segment aligned.

**Private-network access** is allowed by default (`GATEHOUSE_PROXY_ALLOW_PRIVATE` is unset or anything other than `"false"`). This matches the homelab posture where your services live on `10.x` or `192.168.x` and blocking them by default would make the proxy useless. For deployments exposed to the public internet, set `GATEHOUSE_PROXY_ALLOW_PRIVATE=false` to fail-closed against `127.x`, `169.254.169.254`, `10.0.0.0/8`, etc., and selectively re-enable per secret with `metadata.allow_private=true`.

The per-secret `allowed_domains` allowlist is the primary host-scoping control. The private-network flag is defense-in-depth for the SSRF class specifically.

`write` on a secret is equivalent to being able to disclose it: whoever can edit a secret's `allowed_domains` or `upstream_url` can point it at a host they control and receive the injected credential. Grant `write` only to principals you would trust with the value.

### Passthrough

[Passthrough](/docs/passthrough/) (`/p/<alias>/...`) runs the same controls as `/v1/proxy` through the same shared code. The caller never chooses the upstream host: it comes only from the secret's `upstream_url`. No Gatehouse credential is forwarded upstream, and an alias grants nothing without a policy that gives the caller `proxy` on the secret.

A passthrough key (`gatehouse_pt_...`) is the AppRole's `role_id` and `secret_id` in one token, so treat it exactly like the `secret_id`: anyone holding it can act as that AppRole until it is revoked. Gatehouse stores nothing new for it. Rotate the AppRole's `secret_id` to revoke every passthrough key built from the old one; a verified key is cached for at most 5 minutes, and the cache entry is bound to the stored secret hash, so a rotation takes effect on the next request. Suspension and the AppRole's IP allowlist are read on every request and never cached. Failed key checks count against the per-IP login limiter. Only passthrough-key checks do: on `/p/`, as on `/v1`, a JWT or the root token is verified without the limiter, so anonymous or junk requests cannot lock a source IP out of passthrough.

The response scrubber replaces whole occurrences of the secret, including across chunk boundaries, and of its base64 form when the value is Latin1. It matches no other encoding (URL-encoded, JSON-escaped, hex). It skips any redact value shorter than 8 characters, so a secret under 8 characters is never scrubbed (only its base64 form, if that is 8 or more). It does not recognise a fragment: an upstream that echoes only part of the key passes that part through. All of this is true of `/v1/proxy` as well.

### SSO assurance shift

When SSO is enabled, the IdP becomes the identity authority for the human-account login path. Specifically:

- **Local TOTP is bypassed** for SSO logins, even if the user has TOTP enrolled at Gatehouse. The assumption is the IdP is enforcing its own MFA.
- The `email_verified` claim on the OIDC userinfo response is the safety net against IdPs that let users self-attest emails. Default-strict; the per-deployment `trust_unverified_email` opt-in exists for IdPs (PocketID) that intentionally omit the claim because the email is administrator-controlled at the IdP.
- Username and access-token login paths still require local TOTP per the user's enrollment. SSO is the only path that defers MFA to the IdP.

If your IdP's authentication assurance is weaker than your local TOTP setup, leave SSO disabled. The SSO docs page details the model.

## Cryptographic details

- **Symmetric encryption:** XSalsa20-Poly1305 via `tweetnacl`. Per-secret random 32-byte DEK, encrypted with a KEK derived from the master key via HKDF-SHA256 with a domain separation label.
- **Password hashing:** Argon2id via `Bun.password.hash`. Gatehouse passes no options, so the cost parameters are Bun's Argon2id defaults, and each stored hash records the parameters it was made with.
- **JWT signing:** HS256 with the `GATEHOUSE_JWT_SECRET` env var (if unset, derived from the master key with HKDF on every start; nothing is persisted).
- **TOTP:** RFC 6238, SHA1, 6 digits, 30-second period.
- **Recovery codes:** 10 one-time codes per user, each 8 characters, hashed with Argon2id before storage.
